# 과제 시작: 분석 → 질문 → 계약

이 단계에서는 **코드, 설정, 의존성을 바꾸지 않는다.** 읽고 정리만 한다.

## 1. 읽기 (10분 이내)

1. 과제 README 전체, 파일 목록(`ls -la`, `find . -maxdepth 2`), 제출 형식, 필수 파일명을 확인한다.
2. 데이터 파일은 통째로 열지 않는다. `python3 .hk/tools/profile.py <파일>`로 요약만 본다.
3. 실행 환경을 확인한다: `python3 .hk/tools/preflight.py --env`
4. 사용자에게 시작 시각과 작업 시간(분)을 받아 TASK.md 상단에 적는다.
5. `git status`로 저장소인지 확인한다. 아니면 사용자에게 묻고 `git init` 후 첫 커밋을 만든다. 단계별 커밋이 작업 과정의 증거가 된다.

## 2. 분류해서 보여주기

다음 형식으로 사용자에게 보여주고 `TASK.md`에 옮긴다. 각 항목에 근거 위치(`README:줄`)를 붙인다.

```
한 문장: 나는 ___를 만든다. ___는 하지 않는다.
사실(문서에 문자로 적힌 것) / 가정(내가 정한 것, 틀리면 깨지는 것) /
열린 질문(담당자만 답할 수 있는 것) / 안 할 일(과설계 방지)
필수 산출물 → 필요한 입력 → 데이터가 뒷받침하는지 → 빠진 것(GAP)
```

핵심 기능이 추정이면 그 확인이 첫 질문이다.

## 3. 담당자 인터뷰

담당자(시나리오 에이전트)는 사용자가 메신저로 묻는다. Codex는 **질문 초안만** 만든다.

**순서**: 해법 단어(자동화, AI, 대시보드)는 처음에 꺼내지 않는다.

| 단계 | 묻는 것 | 예시 |
|---|---|---|
| 상황 | 최근 실제 사례 하나 | "이 문제가 최근에 실제로 어떻게 벌어졌나요?" |
| 현재 방식 | 지금 누가 어떻게 처리하나 | "지금은 엑셀이나 수작업으로 하시나요? 누가 하나요?" |
| 결과 사용 | 결과를 누가 보고 무엇을 결정하나 | "이 결과를 보고 어떤 판단을 하시나요?" |
| 성공 기준 | 숫자, 현재값, 측정 위치 | "잘됐다는 걸 어떤 숫자로 아시나요? 지금은 얼마인가요?" |
| 비용 | 틀렸을 때 어느 쪽이 더 비싼가 | "놓치는 것과 잘못 거르는 것 중 어느 쪽이 더 문제인가요?" |
| 경계 | 예외, 제외, 동률, 경계값 | "기준값과 정확히 같으면 통과인가요?" |
| 데이터 의미 | 결측, 0, 중복, 재검사의 뜻 | "값이 비어 있는 건 측정을 안 한 건가요, 0인가요?" |

- 한 번에 1~2개만 묻는다. 답을 받으면 한 번 더 파고든다(왜? 그럼 이 경우는?).
- 답을 기다리는 동안 독립적인 작업(데이터 프로파일, 환경 확인)을 진행한다.
- 담당자 답변은 원문 요지 그대로 TASK.md 열린 질문 표에 적는다. AI 해석과 구분한다.
- 이미 README에 답이 있는 것은 묻지 않는다.

## 4. 합의문

구현 전에 아래를 사용자에게 보여주고 승인을 받는다. 필요하면 사용자가 담당자에게 확인한다.

```
문제:
원인(병목):
성공 기준: 지표 / 목표값 / 비교 기준
만들 것:
안 만들 것:
제약:
완료 조건: 문장 → 테스트 이름
```

승인되면 TASK.md의 Status를 `ACTIVE`로 바꾸고 커밋한다: `git add -A && git commit -m "docs: 과제 계약 확정"`
