# 핵심 로직 설계: 고르기 전에 비교, 풀기 전에 검증기

핵심 로직은 Codex가 혼자 정하지 않는다. 이 스킬은 선택지를 만들고, 사용자가 고르고, 기록하게 한다.

## 1. 문제 유형 분류

README와 담당자 답변으로 먼저 분류한다. 섞여 있으면 나눠서 각각 정한다.

| 유형 | 신호 | 기본 접근 | 함정 |
|---|---|---|---|
| 규칙 판정 | 기준값, 규격, 정책 문서, "~이면 불량" | 규칙 표 + 판정 함수 + 경계 테스트 | 경계값(`>=` vs `>`), 예외 우선순위, 규칙 충돌 |
| 집계와 보고 | 수율, 추이, 비교, 리포트 | 계산 스크립트 + 검산 | 분모, 단위, 조인 증폭, 기간 경계 |
| 예측과 분류 | 라벨이 있는 과거 데이터, "미리 알고 싶다" | 기준선 → 단순 모델 → 개선 | 누수, 분할, 불균형, 지표 선택 |
| 이상 탐지 | 라벨이 없거나 극소수, "평소와 다르면" | 통계 기준(관리한계, 분위수) → 필요시 모델 | 기준 구간 오염, 알람 과다 |
| 배정과 스케줄링 | 자원, 용량, 시간창, "누구를 어디에" | 필수 제약 검증기 → 탐욕 기준선 → 개선 | 필수와 선호 혼동, 동점 처리, 실행 불가능 입력 |
| 우선순위와 추천 | 순위, 대기열, "먼저 볼 것" | 설명 가능한 점수식 → 담당자 확인 | 가중치 근거 없음, 점수 동률 |
| 텍스트와 문서 | 로그 문구, 매뉴얼, 보고서 | 규칙과 키워드 먼저, LLM은 보조 | 근거 없는 요약, 재현 불가능한 출력 |

**LLM을 결과의 판정자로 쓰지 않는다.** 같은 입력에 같은 출력이 나와야 하는 판정, 계산, 배정은 코드가 한다. LLM은 해석, 요약, 초안, 분류 후보 제시에만 쓰고 그 출력은 코드로 검증한다.

## 2. 조건을 세 칸으로 나눈다

TASK.md에 표로 적는다. 담당자 답변이 근거다.

| 필수 제약 (어기면 결과 무효) | 목표 (좋을수록 좋음, 단위 포함) | 선호 (가능하면) |
|---|---|---|
| 예: 장비 용량 초과 금지 | 예: 평균 대기 시간 최소 | 예: 같은 lot은 같은 장비 |

- 필수 제약과 목표를 섞어 하나의 점수로 만들지 않는다. 섞으면 결과를 설명할 수 없다.
- 목표가 둘 이상이면 우선순위(사전식)인지 가중합인지 사용자가 정한다.
- 입력이 필수 제약을 만족할 수 없는 경우의 동작(오류, 부분 결과, 보류)을 정한다.

## 3. 선택지 제시 (사용자가 고름)

2~3개를 이 형식으로 보여준다.

```
선택지 A: (이름)
  방법: 한 줄
  장점: 설명 가능성 / 구현 시간 / 성능
  단점: 어디서 틀리나
  판별 사례: A와 B가 다른 결과를 내는 작은 입력 하나
추천: X. 이유: (남은 시간, 데이터 크기, 담당자 기준)
```

- **판별 사례**가 핵심이다. 선택에 따라 결과가 달라지는 입력을 하나 보여줘야 사용자가 의미 있게 고를 수 있다. 그 사례는 테스트가 된다.
- 사용자가 고르면 DECISIONS.md에 `결정 / 버린 대안 / 이유 / 판별 사례`를 남긴다. 사용자가 Codex 추천과 다르게 고르면 사람 개입 표에도 남긴다.
- 남은 시간이 부족하면 가장 단순하고 설명 가능한 것을 추천한다.

## 4. 검증기를 풀이기보다 먼저

배정, 스케줄링, 규칙 판정, 집계처럼 정답 조건이 정해진 문제는 **결과를 검사하는 검증기**를 먼저 만든다.

- 검증기는 풀이 코드와 **다른 파일, 다른 함수**로 만들고 풀이 코드를 import하지 않는다.
- 필수 제약 하나당 검사 하나. 위반은 `제약 이름 / 대상 / 실제값 / 기준` 한 줄로 출력한다.
- 손으로 만든 정답 예시 1개와 일부러 틀린 예시 1개로 검증기를 먼저 확인한다(틀린 예시에서 FAIL이 나와야 한다).
- 목표 값(대기 시간 합계, 처리량 등)도 검증기에서 독립적으로 계산한다.

## 5. 기준선 → 개선

1. 가장 단순한 방법(규칙, 탐욕, 다수 클래스, 평균)으로 끝까지 돌려 기준선 수치를 얻는다.
2. 개선은 한 번에 하나씩, 기준선 대비 수치로 비교한다. 결과는 DECISIONS.md에 표로 누적한다.
3. 개선이 기준선보다 작거나 설명하기 어려우면 기준선을 제출한다.
4. 같은 입력을 두 번 넣어 같은 결과가 나오는지 확인한다(난수 시드, 정렬 안정성, 동점 규칙).

## 6. 새 라이브러리

OR-Tools, LightGBM 같은 라이브러리는 `preflight.py --env`로 있는지 먼저 본다. 없으면 표준 라이브러리나 이미 있는 것으로 가능한지 먼저 검토하고, 설치가 필요하면 사용자에게 묻는다. 설치에 5분 이상 쓰지 않는다.
