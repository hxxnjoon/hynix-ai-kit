# 마무리: 동결 → 정리 → 설명 준비

**이 단계부터 새 기능을 추가하지 않는다.** 남은 시간이 부족하면 기능을 줄이고 한계로 기록한다.

## 1. 결과물 README (심사자가 가장 먼저 본다)

과제가 지정한 양식이 있으면 그것을 따른다. 없으면 이 순서로, 항목당 3줄 이내.

```markdown
# 한 문장: 무엇을 만들었나
## 결론 (핵심 수치와 비교 기준)
## 실행 방법          ← 실제로 쳐본 명령만
## 방법과 주요 결정    ← DECISIONS.md 요약
## 하지 않은 것과 이유
## 한계와 다음 검증
```

- `TODO`, `___`, `미구현`, 템플릿 문구가 남지 않게 한다.
- README의 실행 명령을 실제로 다시 실행해 확인한다.

## 2. 기록 정리

- TASK.md 완료 조건 상태가 실제 테스트 결과와 같은지 대조한다.
- DECISIONS.md에 사람 개입 기록, 실패 지점, 쓴 외부 자료 출처가 있는지 확인한다.
- `python3 .hk/tools/preflight.py` → FAIL 0 또는 FAIL 사유를 한계로 기록.
- 커밋: `git add -A && git commit -m "docs: 최종 정리"`

## 3. FINAL_REVIEW.md (서술형 대비, 제출 전 사용자 리허설용)

후속 서술형은 **제출물과 작업 기록을 바탕으로 생성되고, AI 없이 문항당 5분 안에 직접 타이핑**한다.
`.hk/templates/FINAL_REVIEW.md`를 과제 루트로 복사해 채운다. **실제 기록에 있는 사실만** 쓴다.

1. **숫자 카드** (외워 갈 것): 데이터 크기, 타깃 비율, 주 지표 값과 기준선 값, 제외한 컬럼과 이유, 테스트 개수
2. **결정 카드 3개**: 결정 / 버린 대안 / 이유 / 근거 수치
3. **약점 카드 3개**: 어떤 입력에서 틀리나 / 왜 위험한가 / 다음에 무엇을 검증하나
4. **AI 경계 카드**: Codex에 맡긴 것 / 사용자가 직접 정한 것 / Codex 출력을 믿지 않고 다시 확인한 지점과 방법
5. **예상 질문 8개**: 이 결과물에 해당하는 것만 골라 아래 은행에서 고른다

### 질문 은행

- 이 결과를 누가 보고 어떤 결정을 바꾸나요?
- 문제에 없던 것 중 무엇을 가정했나요? 그 가정이 틀리면 무엇이 깨지나요?
- 하지 않기로 한 것은 무엇이고 왜인가요?
- 이 지표를 고른 이유는? 정확도를 쓰지 않은 이유는?
- 데이터 누수를 어떻게 확인했나요? 분할 방식은 왜 그렇게 했나요?
- 이 숫자는 어느 코드에서 어떻게 계산됐나요?
- 결과물이 가장 먼저 깨지는 입력이나 상황은?
- 데이터가 10배가 되면 어디가 먼저 문제인가요?
- Codex의 출력을 어디서 믿지 않았나요?
- 중간에 방향을 바꾼 적이 있나요? 무엇을 보고 바꿨나요?
- 실패하는 테스트를 실제로 본 적이 있나요?
- 내일 현장에 넣는다면 무엇을 먼저 확인해야 하나요?

### 답변 골격 (5분, 4~6문장)

```
판단  → "저는 X로 정했습니다."
이유  → "Y 때문입니다. (근거 수치나 담당자 답변)"
확인  → "Z로 검증했고 결과는 N이었습니다."
한계  → "다만 W인 경우에는 틀릴 수 있어 V를 추가로 확인해야 합니다."
```

질문의 전제가 실제 구현과 다르면 첫 문장에서 바로잡는다: "제 구현은 ~입니다."
확인하지 않은 것은 "확인하지 않았습니다. 확인하려면 ~를 보면 됩니다."라고 쓴다.

## 4. 제출

- 종료 10분 전에는 제출을 시작한다.
- FINAL_REVIEW.md를 사용자가 소리 내어 한 번 읽게 한다. 막히는 질문이 있으면 그건 기록에 없는 것이니 한 줄 추가한다.
- 제출 확정 후에는 AI를 쓰지 않는다.
